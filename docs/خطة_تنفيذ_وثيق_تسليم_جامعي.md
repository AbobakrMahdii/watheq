# خطة تنفيذ مشروع "وثيق" – نسخة التسليم الجامعي

تهدف هذه الخطة إلى تمكين فريق مكوَّن من ستة طلاب (مع قابلية التنفيذ من شخص واحد بالتسلسل) من إنجاز نسخة أكاديمية قابلة للعرض من مشروع "وثيق" خلال فصل دراسي. ركّزنا على التفاصيل العملية، مع تمييز واضح بين العناصر **الأساسية** التي تضمن اكتمال المشروع، والعناصر **البونص** التي تحسّن الجودة، والأنشطة **المبالغ فيها** (Overkill) التي لا تُنصح بها في سياق مشروع تخرج.

## نظرة سريعة

- **زمن التنفيذ المقترح:** 10–12 أسبوعًا.
- **التقنيات الأساسية:**
  - باك إند: Python 3.11، FastAPI، SQLite (اختياري PostgreSQL)، SQLAlchemy.
  - الذكاء الاصطناعي: EasyOCR، face_recognition، scikit-image (لـ SSIM)، OpenCV، PyTorch (مطلوب فقط للبونص).
  - الواجهة: React + Vite + Tailwind CSS _أو_ واجهة أبسط باستخدام Streamlit (للفريق الأقل خبرة).
  - التخزين: نظام ملفات منظم + SQLite. (البونص: إضافة TinyDB أو Firestore). (المبالغ فيه: Hyperledger Fabric + IPFS).
  - التوثيق والإدارة: Notion/Google Docs، Trello/ClickUp، GitHub أو GitLab.
- **آلية العمل:** تقسيم الخطة إلى مسارات قابلة للتنفيذ بالتوازي (ستة مسارات)، مع دليل تفصيلي لكل مهمة.

## المرحلة 1: تحليل المتطلبات والتصميم المبسط (أسبوع)

### المرحلة 1 – ما يجب إنجازه (أساسي)

1. **قراءة جماعية لوثيقة المتطلبات** وتلخيص الوظائف الأساسية التالية:
   - رفع وثيقة (صورة/ PDF) والتحقق من البيانات.
   - استخراج النص من الوثيقة (OCR).
   - الكشف عن التعديلات في الأختام/التوقيعات.
   - التحقق من صورة الوجه مقارنة بالسيلفي.
   - عرض النتائج في لوحة إدارة مبسطة.
2. **صياغة User Stories** بصيغة: "كمستخدم [نوع] أحتاج إلى [وظيفة] حتى [قيمة]".
3. **رسم معماري مبسط** باستخدام draw.io أو Whimsical:
   - على مستوى واحد (C4 Level 1):
     - واجهة (Web أو Streamlit).
     - REST API (FastAPI).
     - خدمات الذكاء الاصطناعي (OCR، كشف التزوير، التحقق البيومتري).
     - قاعدة بيانات SQLite.
   - حفظ الرسم في المستودع.
4. **تحديد تبعيات كل وحدة**:
   - OCR → EasyOCR + OpenCV.
   - كشف التلاعب → OpenCV + scikit-image (خوارزمية SSIM).
   - التحقق البيومتري → face_recognition.
   - واجهة → React (بديل Streamlit).
5. **توثيق خطة البيانات** (أين تُحفظ الملفات، كيف تُسمى، ما الامتدادات المقبولة).

### المرحلة 1 – تحسينات اختيارية (بونص)

- إنشاء نموذج أولي بسيط على Figma لواجهة الإدارة.
- كتابة وثيقة مخاطر مختصرة (أكبر 5 مخاطر وكيفية التعامل معها).

### المرحلة 1 – أنشطة مبالغ فيها (تُتجنب)

- تصميم Microservices منفصلة، أو اعتماد Message Broker.
- وضع معايير Enterprise Architecture أو TOGAF.

## المرحلة 2: إعداد البيئة والبيانات (أسبوع)

### المرحلة 2 – ما يجب إنجازه (أساسي)

1. **تهيئة بيئة التطوير** على كل جهاز:
   - تثبيت Python 3.11 وGit.
   - إنشاء بيئة افتراضية: `python -m venv .venv` ثم التفعيل.
   - تثبيت المتطلبات الأولية: `pip install fastapi uvicorn[standard] easyocr opencv-python-headless scikit-image face-recognition python-multipart sqlalchemy alembic`.
2. **إنشاء هيكل المشروع**:
   - مجلد `backend`، `frontend`، `ai_models`, `docs`, `data`.
   - ملف `README.md` يشرح خطوات التشغيل.
3. **تجميع مجموعة بيانات صغيرة**:
   - 10–15 صورة وثيقة (هوية، شهادة ميلاد،...) + سيلفي مطابق لكل وثيقة.
   - 5 أمثلة مزوّرة (تعديلات يدوية على صورة بخط أحمر أو طمس الختم) لإثبات الفكرة.
   - حفظها في `data/raw` مع تسمية موحّدة (`doc_01_front.jpg`, `doc_01_selfie.jpg`).
4. **إنشاء سكربت تنظيم بيانات** (`ai_models/prepare_data.py`) ينقل الملفات إلى بنية:
   - `data/processed/ocr`, `data/processed/forgery`, `data/processed/face`.
5. **إعداد قاعدة بيانات SQLite** عبر سكربت `backend/init_db.py` يحتوي جداول:
   - `documents(id, user_name, document_type, upload_path, created_at)`.
   - `ocr_results(document_id, extracted_text, confidence)`.
   - `verification_results(document_id, seal_score, signature_score, face_score, overall_status)`.

### المرحلة 2 – تحسينات اختيارية (بونص)

- تهيئة Docker Compose بسيط لتشغيل FastAPI + SQLite + واجهة React.
- استخدام DVC لتتبع نسخ البيانات.

### المرحلة 2 – أنشطة مبالغ فيها (تُتجنب)

- إعداد Kubernetes أو Terraform.
- استخدام PostgreSQL مع نسخ احتياطي يومي.

## المرحلة 3: تطوير المكونات الأساسية (أسبوعان إلى ثلاثة)

### 3.1 خدمة OCR مبسطة

#### 3.1 – ما يجب إنجازه (أساسي)

1. إنشاء ملف `backend/services/ocr_service.py` يحتوي دالة `extract_text(image_path)`:
   - استخدام `easyocr.Reader(['ar', 'en'])`.
   - إرجاع النص مع درجة الثقة.
2. تطوير Endpoint `POST /api/ocr` في `backend/main.py`:
   - استقبال ملف عبر `UploadFile`.
   - حفظه مؤقتًا في `data/uploads`.
   - استدعاء `extract_text` وتخزين النتائج في SQLite.
3. إنشاء اختبار باستخدام pytest (`tests/test_ocr.py`) يتحقق من نجاح استخراج نص قصير.
4. تحديث README بخطوات تشغيل الخدمة: `uvicorn backend.main:app --reload`.

#### 3.1 – تحسينات اختيارية (بونص)

- إضافة مرحلة تنظيف للصور (تحويل إلى رمادي، تحسين التباين).
- دعم رفع ملفات PDF متعددة الصفحات (تحويل عبر `pdf2image`).

#### 3.1 – أنشطة مبالغ فيها (تُتجنب)

- تدريب نموذج TrOCR مخصَّص من الصفر.
- بناء خدمة OCR موزعة باستخدام TorchServe.

### 3.2 الكشف البصري عن التلاعب

#### 3.2 – ما يجب إنجازه (أساسي)

1. إنشاء ملف `backend/services/forgery_service.py`:
   - اعتماد خوارزمية SSIM من `skimage.metrics` لمقارنة الوثيقة بنسخة مرجعية (إن وجدت).
   - في حال عدم وجود مرجع، تطبيق كشف الحواف Highlight (Canny) وإرجاع خريطة لونية بسيطة.
2. Endpoint `POST /api/forgery`:
   - استقبال صورتين (الأصلية + الحالية) إن توفرتا، أو صورة واحدة.
   - حساب درجة التشابه (0–1) ووضع عتبة (مثلاً 0.75) لتحديد الحالة.
3. حفظ النتيجة في جدول `verification_results` مع `seal_score` و`signature_score` (قيم تقريبية من نفس الخوارزمية).
4. كتابة اختبار مصطنع يقارن صورة أصلية ونسخة معدلة (إحداث تغيير بسيط عبر OpenCV) للتأكد من انخفاض الدرجة.

#### 3.2 – تحسينات اختيارية (بونص)

- تطبيق تحليل منطقة الاهتمام (ROI) يدوياً بإتاحة تحديد مناطق التوقيع/الختم.
- توليد تقرير بصري بصيغة Heatmap باستخدام matplotlib.

#### 3.2 – أنشطة مبالغ فيها (تُتجنب)

- استخدام نموذج GAN للكشف عن التزوير.
- دمج شبكة Mask R-CNN أو EfficientNet للتعرف على الأختام.

### 3.3 التحقق البيومتري البسيط

#### 3.3 – ما يجب إنجازه (أساسي)

1. ملف `backend/services/face_service.py` يستخدم مكتبة `face_recognition`:
   - دالة `compare_face(document_face_path, selfie_path)` تُرجع درجة تشابه ومسافة Euclidean.
   - تحديد عتبة قبول (مثلاً مسافة ≤ 0.6).
2. Endpoint `POST /api/face-verify` يستقبل صورتين ويعيد نسبة التطابق والحالة النهائية.
3. إضافة وحدة اختبار بصور التجربة (`tests/test_face.py`).
4. تخزين النتائج في قاعدة البيانات وربطها بالوثيقة.

#### 3.3 – تحسينات اختيارية (بونص)

- إضافة خطوة كشف حيوية بسيطة (طلب صورتين مع حركة مختلفة والتحقق من اختلافهما).
- إنشاء سكربت `scripts/crop_face.py` لقص الوجوه تلقائياً من الوثيقة.

#### 3.3 – أنشطة مبالغ فيها (تُتجنب)

- إدراج نظام Liveness متقدم أو تكامل مع أجهزة ثلاثية الأبعاد.
- اعتماد شبكات عصبية مُدربة ذاتيًا (ArcFace) من الصفر.

### 3.4 واجهة المستخدم ولوحة الإدارة

#### 3.4 – ما يجب إنجازه (أساسي)

1. اختيار أحد الخيارين:
   - **React + Vite:**
     - `npm create vite@latest frontend -- --template react`
     - تثبيت Axios وTailwind.
     - إنشاء صفحات: تسجيل الدخول الوهمي، رفع الوثيقة، عرض النتائج.
   - **Streamlit (بديل أسهل):**
     - `pip install streamlit`
     - بناء صفحة واحدة تعرض نموذج رفع ملفات وتستدعي Endpoints السابقة.
2. توفير شاشة تعرض قائمة الوثائق (جلب `GET /api/documents`).
3. شاشة تفاصيل الوثيقة تعرض:
   - النص المستخرج.
   - درجات الكشف عن التلاعب.
   - نتيجة التحقق البيومتري.
4. إضافة زر "إعادة الاختبار" لإعادة إرسال البيانات إلى API.

#### 3.4 – تحسينات اختيارية (بونص)

- دعم الترجمة (عربي/إنجليزي) باستخدام `react-i18next` أو إعداد واجهة Streamlit ثنائية اللغة.
- تصميم بطاقة تقرير PDF باستخدام `ReportLab`.

#### 3.4 – أنشطة مبالغ فيها (تُتجنب)

- تطوير لوحة تحكُّم معقدة بـ Next.js وStorybook.
- دمج نظام إشعارات آنية أو Push Notifications.

### 3.5 الربط وتدفق العمل

#### 3.5 – ما يجب إنجازه (أساسي)

1. تحديث `backend/main.py` لإضافة Endpoint موحّد `POST /api/process-document` يُنفِّذ:
   - حفظ الملف.
   - استدعاء OCR → كشف التلاعب → التحقق البيومتري (إذا توفرت صور).
   - تجميع نتيجة نهائية وإرجاعها للواجهة.
2. إنشاء سكربت `scripts/demo_workflow.py` يسمح بتجربة سطر أوامر:
   - `python scripts/demo_workflow.py --doc data/sample/doc_01.jpg --selfie data/sample/doc_01_selfie.jpg`.
3. كتابة اختبار تكاملي `tests/test_full_flow.py` يفحص تدفق كامل باستخدام ملفي عينة.

#### 3.5 – تحسينات اختيارية (بونص)

- إضافة Queue بسيطة باستخدام `RQ` لمعالجة الملفات الكبيرة دون حظر الطلبات.
- تسجيل الأحداث في ملف `logs/app.log`.

#### 3.5 – أنشطة مبالغ فيها (تُتجنب)

- بناء نظام رسائل (RabbitMQ) أو بنية Microservices منفصلة.
